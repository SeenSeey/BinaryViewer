# Statement of Work: поддержка Windows для Binary Viewer

## 1. Назначение документа

Этот документ является техническим заданием для агента, который должен добавить в
существующий репозиторий полноценную сборку Binary Viewer для Windows.

Работа выполняется **в текущем репозитории**. Создавать отдельный Windows-репозиторий,
копировать исходный код или вести отдельную Windows-ветку продукта не требуется.

Итогом должна стать воспроизводимая Windows x64 сборка, проходящая тесты и
поставляемая как самодостаточный portable-архив, который запускается на машине без
предварительно установленного Qt.

## 2. Контекст проекта

Текущее приложение:

- написано на C++20;
- использует Qt Widgets и Qt 5.15 (`Core`, `Gui`, `Widgets`, `Test`);
- собирается с помощью CMake 3.16+;
- имеет разделение на `core`, `presentation` и `ui`;
- читает файлы через `QFile` и не использует POSIX API в production-коде;
- встраивает стили через Qt Resource System;
- содержит четыре автоматических тестовых исполняемых файла;
- в текущем Linux-окружении собирается, а все четыре теста проходят.

Linux-специфичный код присутствует только в test helper для обработки редкого
случая безымянного `QTemporaryFile` через `/proc/self/fd`. Это не является
зависимостью приложения от Linux.

Основные файлы:

- `CMakeLists.txt` — корневая сборка;
- `tests/CMakeLists.txt` — тестовые цели;
- `src/main.cpp` — запуск GUI;
- `src/core/BinaryFileReader.*` — чтение файлов;
- `src/core/ViewerSession.*` — состояние просмотра;
- `src/ui/*` — Qt Widgets интерфейс;
- `resources/resources.qrc` — встроенные ресурсы;
- `README.md` — пользовательская документация.

## 3. Целевой результат

После выполнения работы репозиторий должен поддерживать две платформы из
одной кодовой базы:

1. существующую Linux-сборку;
2. Windows 7/10/11 x64.

Для Windows должны быть доступны:
- локальная сборка с MSVC x64;
- автоматическая сборка и тестирование в GitHub Actions;
- Release-артефакт в формате ZIP;
- запуск `BinaryViewer.exe` без консольного окна;
- запуск portable-пакета без установленного Qt и без зависимости от Qt в `PATH`;
- инструкция по локальной сборке, тестированию и упаковке.

## 4. Обязательные ограничения по архитектуре
1. Сохранить одну общую кодовую базу для Linux и Windows.
2. Не создавать копии `src`, `tests` или ресурсов для Windows.
3. Платформенные различия по возможности выражать в CMake или packaging-скриптах.
4. Не добавлять `#ifdef Q_OS_WIN` в бизнес-логику без доказанной необходимости.
5. Не менять поведение конвертации байтов, навигации, выделения и чтения файлов.
6. Не ухудшать существующую Linux-сборку и тесты.
7. Не коммитить бинарники, Qt DLL, build-каталоги и собранные ZIP-файлы.
8. Не выполнять посторонний рефакторинг, переименование модулей или изменение API.

## 5. Зафиксированные технические решения

### 5.1. Qt

Обязательный baseline — используемый проектом Qt 5.15. Агент не должен связывать
добавление Windows с обязательной миграцией на Qt 6.

Допускается сделать CMake совместимым одновременно с Qt 5 и Qt 6, только если это:
- не увеличивает существенно объём изменений;
- не ломает Qt 5.15;
- подтверждено тестами на доступных конфигурациях;
- отдельно объяснено в итоговом отчёте.

Если Windows toolchain с Qt 5.15 недоступен в выбранной CI-среде, агент должен
сначала попытаться подобрать совместимую версию MSVC/Qt. Переход на Qt 6 допустим
только как явно обоснованное решение, а не как неявная замена зависимости.

### 5.2. Компилятор и архитектура

Основная Windows-конфигурация:

- MSVC;
- x64;
- C++20;
- Release для распространяемого артефакта.

MinGW может быть дополнительно поддержан, но не заменяет обязательную MSVC-сборку,
если нет документированного технического ограничения среды.

### 5.3. Формат поставки

Обязательный результат — portable ZIP. Установщик MSI/EXE, публикация GitHub
Release и code signing не входят в основной объём этой задачи.

Portable-пакет должен собираться из отдельного staging-каталога. Нельзя формировать
его непосредственно из исходников или всего build-каталога.

## 6. Объём работ

### 6.1. Адаптация CMake

Агент должен обновить CMake-конфигурацию так, чтобы:

1. `BinaryViewer` на Windows собирался как GUI-приложение без консольного окна.
2. Linux сохранил текущее поведение сборки.
3. Для MSVC была явно включена корректная обработка UTF-8 исходников (`/utf-8`).
   Это необходимо из-за Unicode-символов в UI: стрелок, знака минус, эм-даш и
   декоративного символа в заголовке.
4. Предупреждения компилятора были настроены платформенно:
   - сохранить `-Wall -Wextra -Wpedantic` для GNU/Clang;
   - добавить разумный уровень предупреждений для MSVC, например `/W4`;
   - не включать глобальный `warnings as errors`, если это ломает Qt headers.
5. Была добавлена install-цель для исполняемого файла, пригодная для формирования
   staging-каталога.
6. Debug и Release артефакты не смешивались.
7. Multi-config генераторы CMake корректно обрабатывались через `--config`.

Рекомендуемый подход — использовать свойства цели и target-specific options, а не
глобальные `CMAKE_CXX_FLAGS`.

### 6.2. Windows metadata

Добавить Windows resource-файл только если он может быть заполнен корректными
данными проекта. Он может содержать:

- имя продукта `Binary Viewer`;
- версию из CMake project version;
- описание файла;
- имя исполняемого файла.

Не придумывать и не генерировать новый логотип в рамках этой задачи. Если готовой
иконки `.ico` в репозитории нет, то взять иконку, отображаемую на главном экране приложения рядом с надписью "Binary Viewer".

### 6.3. Автоматическая упаковка

Добавить воспроизводимый Windows packaging-шаг, который:

1. создаёт чистый staging-каталог внутри build/output области;
2. устанавливает или копирует туда только Release-версию `BinaryViewer.exe`;
3. запускает `windeployqt` из того же Qt installation, которым собран проект;
4. добавляет необходимые Qt DLL и плагины, включая Windows platform plugin;
5. не включает debug DLL в Release-пакет;
6. проверяет код возврата каждой операции и завершается с ошибкой при сбое;
7. создаёт ZIP с однозначным именем, например
   `BinaryViewer-<version>-windows-x64.zip`;
8. не зависит от Qt, случайно найденного первым в системном `PATH`.

Packaging можно реализовать через CMake и/или отдельный PowerShell-скрипт в
`packaging/windows/`. Скрипт должен принимать пути параметрами или получать их из
CMake, не содержать абсолютных путей конкретного разработчика и работать с путями,
содержащими пробелы.

Минимально ожидаемое содержимое staging-каталога:

```text
BinaryViewer.exe
Qt5Core.dll
Qt5Gui.dll
Qt5Widgets.dll
platforms/
  qwindows.dll
```

Фактический набор дополнительных библиотек и plugins должен определяться
`windeployqt`. Не следует вручную поддерживать список всех Qt runtime-файлов, если
инструмент может определить его корректно.

### 6.4. GitHub Actions

Добавить отдельный workflow Windows, например `.github/workflows/windows.yml`.

Workflow должен:

1. запускаться минимум на `push` и `pull_request` для основной ветки;
2. использовать поддерживаемый Windows runner;
3. устанавливать или восстанавливать из cache выбранный Qt toolchain;
4. конфигурировать чистый build-каталог с `BUILD_TESTING=ON`;
5. собирать x64 конфигурацию;
6. запускать `ctest --output-on-failure` с правильным `--config` для multi-config
   генератора;
7. создавать portable-пакет только после успешных тестов;
8. публиковать ZIP как workflow artifact;
9. не требовать секретов для обычной PR-сборки;
10. не публиковать GitHub Release автоматически в рамках этой задачи.

Используемые GitHub Actions и инструменты установки Qt должны быть закреплены на
явных стабильных версиях. Агент должен избегать непроверенных скриптов загрузки и
объяснить источник Qt в README или workflow comments.

Предпочтительный порядок job:

```text
checkout
  -> setup compiler and Qt
  -> cmake configure
  -> cmake build
  -> ctest
  -> stage and windeployqt
  -> create ZIP
  -> upload artifact
```

### 6.5. Тесты и Windows-совместимость

Существующие тесты должны собираться и проходить на Windows.

Особое внимание уделить `BinaryFileReaderTests` и `ViewerSessionTests`:

- временный файл должен иметь реальный доступный путь;
- сценарий не должен полагаться на `/proc` в Windows;
- тест должен учитывать Windows file sharing semantics;
- исправление теста не должно ослаблять проверяемое поведение;
- не использовать заранее заданные пути вроде `C:\\Temp`;
- все временные файлы создавать через Qt или системный temporary directory.

Если для Windows временный файл необходимо закрыть перед повторным открытием,
агент должен сначала сбросить данные на диск, сохранить имя файла и обеспечить его
существование до окончания теста. Изменение должно оставаться корректным на Linux.

Добавить новые unit-тесты только при обнаружении реального платформенного дефекта.
Не создавать тесты, которые лишь проверяют наличие `WIN32` macro или конкретный
путь CI runner.

### 6.6. Ручная smoke-проверка

Нужно провести ручную проверку собранного portable-пакета на Windows, если агенту
доступна такая среда. Проверка должна выполняться из распакованного ZIP без Qt в
`PATH`.

Обязательные сценарии:

1. Двойной клик запускает GUI и не открывает console window.
2. Диалог `Open File` открывается и позволяет выбрать файл.
3. Открываются файлы по пути:
   - с пробелами;
   - с кириллицей или другими Unicode-символами.
4. Корректно отображается пустой файл.
5. Корректно отображается непустой бинарный файл.
6. Работают Previous/Next и `PageUp`/`PageDown`.
7. Изменение chunk size не приводит к ошибке навигации.
8. Выделение байтов обновляет binary view.
9. Переключаются Little/Big Endian и размеры слова 16/32/64/128.
10. Ошибка открытия недоступного файла показывается пользователю и не приводит к
    падению.
11. Интерфейс остаётся читаемым при Windows scaling 100%, 125% и, если доступно,
    200%.

Если Windows-среда недоступна, агент обязан явно отметить ручную проверку как не
выполненную. Нельзя заменять её утверждением, что успешная cross-compilation
гарантирует запуск.

### 6.7. Документация

Обновить `README.md` и добавить:

- поддерживаемые платформы;
- Windows prerequisites;
- выбранный MSVC/Qt baseline;
- команды configure, build и test;
- команду или target упаковки;
- расположение итогового ZIP;
- способ запуска portable-версии;
- известные ограничения, если они останутся.

Команды должны быть копируемыми, не содержать путей конкретного разработчика и
явно учитывать multi-config режим, например `--config Release`.

Linux-инструкцию сохранить и отделить от Windows-инструкции.

## 7. Ожидаемые изменения файлов

Минимально ожидается изменение или добавление следующих файлов:

```text
CMakeLists.txt
README.md
.github/workflows/windows.yml
packaging/windows/...          # если используется отдельный packaging-скрипт
resources/windows/...          # только если добавляются metadata/icon resources
tests/...                      # только если существующие тесты требуют адаптации
```

Точная структура может отличаться, если выбранное решение проще и остаётся
воспроизводимым. Не добавлять файлы только ради соответствия этому списку.

## 8. Проверки перед завершением

### 8.1. На Windows

Обязательные автоматические проверки:

```powershell
cmake -S . -B build-windows -DBUILD_TESTING=ON
cmake --build build-windows --config Release --parallel
ctest --test-dir build-windows -C Release --output-on-failure
```

Конкретный generator и путь к Qt могут быть добавлены согласно выбранному
toolchain. Все четыре существующих набора тестов должны завершиться успешно:

- `BinaryConverterTests`;
- `BinaryFileReaderTests`;
- `ViewerSessionTests`;
- `BinaryTextFormatterTests`.

После упаковки нужно проверить, что:

- ZIP действительно создан;
- ZIP распаковывается в отдельный каталог;
- в нём есть `BinaryViewer.exe` и Qt platform plugin;
- приложение запускается без Qt development environment;
- отсутствуют debug Qt DLL в Release artifact.

### 8.2. На Linux

После CMake-изменений обязательно повторить текущий цикл:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Если локальная Linux-среда недоступна, существующий Linux CI должен быть зелёным.
При отсутствии Linux CI агент должен указать этот пробел в итоговом отчёте.

### 8.3. Проверка чистоты пакета и репозитория

Перед завершением проверить:

- отсутствуют случайно добавленные `.exe`, `.dll`, `.obj`, `.pdb`, ZIP и build
  directories;
- workflow artifact создаётся только в CI/output directory;
- нет абсолютных локальных путей;
- нет unrelated изменений;
- diff содержит только работу, относящуюся к Windows support.

## 9. Критерии приёмки

Задача считается выполненной, когда одновременно соблюдены все условия:

1. Один и тот же исходный код собирается на Linux и Windows.
2. Windows x64 Release успешно собирается с MSVC.
3. Все существующие тесты проходят на Windows.
4. Существующие тесты проходят на Linux после изменений.
5. `BinaryViewer.exe` является Windows GUI executable без console window.
6. CI создаёт portable Windows ZIP только после успешной сборки и тестов.
7. ZIP запускается на Windows без установленного Qt.
8. В пакет включены необходимые Qt runtime DLL и `qwindows` platform plugin.
9. Открытие файлов с Unicode-путями подтверждено тестом или ручной проверкой.
10. README содержит актуальные Windows build/package инструкции.
11. В репозиторий не добавлены бинарные результаты сборки.
12. Не осталось известных блокирующих ошибок Windows-сборки.

## 10. Что не входит в задачу

Без отдельного согласования не выполнять:

- создание второго репозитория;
- переписывание UI на WinUI, WPF, MFC или другую технологию;
- обязательную миграцию всего проекта на Qt 6;
- редизайн интерфейса;
- локализацию интерфейса;
- поддержку Windows x86 или ARM64;
- создание MSI/NSIS/WiX installer;
- покупку или настройку code-signing сертификата;
- автоматическую публикацию GitHub Releases;
- ассоциации файлов в реестре Windows;
- добавление auto-update;
- static linking Qt;
- изменение формата отображения бинарных данных.

## 11. Риски и способы их закрытия

### Несовместимость комплекта Qt и MSVC

Использовать один согласованный x64 toolchain. Зафиксировать его в CI и README.
Не смешивать Qt DLL от другого компилятора или архитектуры.

### Приложение собирается, но не запускается вне dev-машины

Формировать пакет через `windeployqt` и проверять распакованный ZIP в окружении без
Qt в `PATH`.

### Консольное окно рядом с GUI

Собирать основной executable с Windows GUI subsystem. Не применять это свойство к
тестовым executable.

### Некорректные Unicode-символы

Включить `/utf-8` target-specific для MSVC и проверить Unicode-путь к файлу.

### Тесты временных файлов падают только на Windows

Проверить lifetime, flush/close и sharing semantics `QTemporaryFile`, не добавляя
Windows-only hardcoded paths.

### Регрессия Linux

Сохранить условные настройки компилятора и выполнить Linux build/tests после
изменения общих CMake-файлов.

### CI работает, но локальная сборка не воспроизводится

Не прятать всю логику внутри workflow. Packaging и build-команды должны быть
доступны локально через CMake target или версионируемый скрипт.

## 12. Требования к итоговому отчёту агента

Итоговый ответ агента должен кратко и доказательно содержать:

1. перечень изменённых файлов;
2. выбранные версии/семейства MSVC и Qt;
3. команды локальной Windows-сборки;
4. способ создания portable ZIP;
5. результаты Windows-тестов;
6. результаты Linux regression-тестов;
7. результат ручной smoke-проверки;
8. ссылку или имя CI artifact;
9. оставшиеся ограничения и риски;
10. любые отклонения от этого SOW с объяснением причины.

Нельзя сообщать, что задача полностью завершена, если агент только написал
workflow, но не подтвердил его успешный запуск, либо если package не был проверен
на отсутствие зависимости от установленного Qt. В таком случае результат должен
быть обозначен как частично реализованный с точным описанием непроверенных пунктов.

## 13. Definition of Done

Работа завершена, когда новый разработчик может клонировать один репозиторий,
выполнить документированные команды на поддерживаемой Windows x64 машине, получить
прошедшую тесты Release-сборку и создать переносимый ZIP, а GitHub Actions повторяет
тот же процесс автоматически без ручной подмены файлов.
